AVG Antivirus intercepts HTTPS on this machine and re-signs every certificate
with its own root:

    subject = CN=github.com
    issuer  = CN=AVG Web/Mail Shield Root, O=AVG Web/Mail Shield,
              OU=generated by AVG Antivirus for SSL/TLS scanning

Git for Windows ships `http.sslbackend=openssl`, which verifies against a fixed
`ca-bundle.crt`. That file is present and valid (3,996 lines) and will never
contain a locally generated root, so every remote call failed with
`SSL certificate problem: unable to get local issuer certificate`.

**Fixed 2026-09-09**, machine-wide:

    git config --global http.sslBackend schannel

schannel uses the Windows certificate store, which already trusts AVG's root
(present in both `LocalMachine\Root` and `CurrentUser\Root`). Verification stays
ON — this is the opposite of `http.sslVerify=false`, which remains the wrong fix
and a security downgrade. Verified: `git ls-remote` returns refs from inside the
agent sandbox. Credential helper is `manager`.

**Why:** it was never a sandbox restriction. The earlier note here concluded "the
same command succeeds in the user's own PowerShell, so it is the sandboxed
environment rather than the machine's git config" — that inference was wrong, and
it cost every session since a manual push step. The differing behaviour was
config, not sandboxing.

**How to apply:** pushes can be run from here now. Still confirm before pushing —
it is outward-facing — rather than pushing unasked.

**Also, still true:** never run `git fetch ... 2>/dev/null` in this repo. It hides
remote failures, and a stale `origin/main` then makes
`rev-list --count HEAD..origin/main` report a reassuring `behind=0` that was never
checked against the remote.
